# 6.7 单 sensor 的预览、主录、备录与拍照

单颗 IMX415 的不同输出可以拥有不同尺寸、帧率或码率，源端曝光和 RAW 模式仍由同一个 sensor 决定。一颗相机怎样让四个消费者共存，先决定哪些数据能共享，再决定哪里要增加缓冲或处理。

## 从一个完整源开始逐层展开

~~~text
IMX415 → CSI/CIF → ISP → 共享原始帧池
                            ├─ 缩放 → 预览
                            ├─ 主编码 → 封装 → 主录像
                            ├─ 独立缩放/编码 → 封装 → 异规格备录像
                            └─ 按快门时间选帧 → JPEG → 静态照片
~~~

视野和真实感光发生在同一个源。用 VPSS 给不同支路缩放，能从 1920×1080 产出 1280×720，但不能让一支在同一个瞬间长曝光、另一支单独短曝光。共用硬件 ISP 时还要看裁剪和处理中哪一部分在分叉前发生。数字变焦可以给一支改变裁切，镜头或传感器控制会影响共同的画面。

本例的 bridge 是应用及媒体模块把一个源接到多个消费者的设计。板端实现要按运行态拓扑验证输入是谁、哪个组件保有帧，以及哪些转换能在硬件或已有通道做。不要把历史设备号、ISP 各节点名称或 MPI 通道号当成四路硬件承诺。硬件一侧的配置方式见 [6.5 Rockchip VI、VPSS、VENC 与 MPP](./rockchip-media.md)。

## 备录像的两种需求在哪里开始分叉

**同规格副本。** 一路编码已能满足主备需求时，在编码或封装完成后复制数据。实验把同一个 streamable Matroska 输出流交给两个 filesink，因此两个文件可逐字节比。产品若要求各文件按不同规则分段，可以从编码流分出两个独立容器；各自的文件头、索引和元数据可能不同，比较的是码流与播放结果。

~~~text
原始帧 → 1 个编码通道 → 1 个封装输出 ┬→ 主写入
                                    └→ 备写入
~~~

两边写同一介质能验证管线分支、文件名字和两次写入。要抵抗介质故障需要独立故障域、分别检测文件健康，也要在备盘掉线时证明主录持续。不同路径名或挂载点不一定意味着不同介质。

**异规格备录。** 在原始帧处分出，给第二路缩小、按要求编码和封装。缩放后再选择编码参数，能降低第二份文件码率，但增加了对缩放通道、编码通道和缓冲池的需求。备录降帧率要保留真实时间含义，不能简单改时间戳加快播放。

~~~text
原始帧 ┬→ 主编码 ───────────────→ 主封装
       └→ 缩放/可选降帧 → 备编码 → 备封装
~~~

## 快门怎样关联到同一个源上的帧

UI 在应用单调时钟记 `T_request`，从采集帧时间戳建立同域映射，再按策略选最接近 T 的帧，或者选 T 之后第一帧。帧保存任务记录源 sequence、原时间戳、选中 PTS、采集参数与支路结果。如果保留最近一帧用于拍照，需要让这份引用尽快结束，或者复制到有上限的拍照池，避免占满共享源。

实验没有物理快门。为保证复现，在 JPEG 支路把合成视频采样为 1 fps，取输出时间戳 1.000 s 的 JPEG 作为模拟快门。这个 PTS 是 videorate 之后的输出时间；实板定位曝光或采样时刻要在重定时前记录源 timestamp 和序号。动态照片需要额外保存快门前后的视频，下一节展开。

## 宿主分五次跑，最后一组接齐四种输出

按[编解码插件环境](./gstreamer.md#local-codecs)启用 H.264 插件，另需 `/usr/bin/time`（Ubuntu 的 time 包）。可<a :href="exampleFile" download="gst-multistream-demo.sh">下载 gst-multistream-demo.sh</a>。脚本每组重新生成同样的 60 帧 30 fps I420，守住一条输入。预览用空 sink，在无桌面的 WSL 也能测试收帧。完整实验日志及文件保存在 `output/gst-multistream.*`。

~~~bash

~~~

| main | 60 帧 | 60 帧解码到 EOS | — | — | 19100 KiB |

主编码设置 512 kbit/s 目标，异规格备录设置 128 kbit/s 目标。两秒的同组样本大小约 147 kB 和 37 kB，实际值由编码器决定。脚本从预览队列日志采集首帧出队时刻，本轮约 18～27 ms，包含宿主管线启动与日志采集开销。RSS 是用户态进程峰值，无法用来直接估算板端 DMA、CMA 与硬件编码占用。60 个不同时间戳证明这一段送到各空 sink 或解码器的数据量。现场完整预览仍需真正显示，录制仍需真实传感器和硬编测试。

## 板端资源预算与故障隔离如何验收

先用一张表给每个消费者记输入实体或通道、输出尺寸、fps、允许等待、队列上限和丢弃策略。上板按预览 → 主录 → 同码流备份或独立备录 → 录像时拍照加量。每步记录首帧时间、sequence 缺口、输入 PTS 到显示或写入的延迟、有效速率、峰值内存、编码通道和文件解码结果。分别模拟备盘变慢和该盘离线，观察主录是否触发告警、中断或按约定降级。

共享 NV12 的 4K 30 fps 有效数据率约 `3840 × 2160 × 1.5 × 30 = 373.248 MB/s`。若内存系统确实承担一次全幅写和两次完整独立读，理想有效载荷量级约 1.12 GB/s。真实总线占用还受对齐、缓存、缩放、行缓冲及硬件通路影响。先在这些路径画出谁写谁读，再照实测数去查 SDK 和板端计数。

| 观察症状 | 首先观察 | 再做的对照 |
| --- | --- | --- |
| 主、备同时掉帧 | 源出队、源池与共享队列 | 关闭第二个编码，看源是否恢复 |
| 预览滞后但录像完整 | 预览帧龄和 queue 水位 | 用有限队列丢旧帧，对比尾延迟 |
| 仅备文件断续 | 备编码出包或备盘写入 | 备录接空 sink，与真实介质对比 |
| 按一次快门让录制短暂停 | 调用线程和原始帧归还时刻 | 将 JPEG/写盘移到独立有界任务 |

## 本节复盘

1. **两份录像逐字节一样，证明了什么？** 同一份封装输出已到达两个文件分支，并能分别解码。本例用同一 WSL 文件系统，介质级容错仍需要独立设备与失效实验。
2. **为什么低分辨率备录像仍可能拖慢高分辨率主录？** 两支竞争源池、处理单元、带宽或写入。先查共享源的缓冲寿命，再查各支路积压。
3. **用哪个时间记录相机快门？** 保留输入帧的原始时间域与序号，记请求时刻并完成换算。支路 PTS 还要考虑重定时、裁切或容器复位。
