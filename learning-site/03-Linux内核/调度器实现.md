# 3.2 调度器与唤醒延迟

线程已经被唤醒，为什么它还过了几毫秒才运行？先在一条 CPU 上读清任务状态、运行队列和切换，再加入另一条 CPU 来解释唤醒与迁移。本节跟读工作区 Linux 6.1 的 CFS 实现。新版本内核的普通调度选择策略可能不同，讨论时先确认版本。[完整学习大纲](../导航/学习大纲.md)

## 3.2.1 从三个对象读调度器

假设一个进程创建读线程 A 和写线程 B。两者能共享地址空间，却仍能在不同 CPU 上执行。内核给每个可调度线程一份 task_struct。调度器选择的是任务，进程的地址空间只是这个任务可能引用的一项资源。

| 对象 | 在哪一级起作用 | 跟读时先找什么 |
| --- | --- | --- |
| task_struct | 一个任务 | __state、on_rq、调度类、允许的 CPU、普通调度的 se |
| rq | 每个 CPU 一份 | curr 指向当前任务，并含各调度类的队列 |
| sched_entity 和 cfs_rq | 普通调度类 | 实体的权重、vruntime 及所属队列。启用组调度时，实体也可以代表一个组 |

三个容易混淆的状态。__state 表达任务当前能否运行或等待什么。on_rq 表达运行队列归属，还可能表示迁移中。SMP 下的 on_cpu 用于标记任务在 CPU 上执行或仍在完成切换。TASK_RUNNING 同时覆盖正在执行和等待执行，想知道这一刻是谁在运行要和目标 rq 的 curr 对照。/proc 的 R 只是观察时的快照。

## 3.2.2 阻塞和抢占共用一个选择点

读线程发现 pipe 为空，依照等待协议登记并准备睡眠。写线程更新数据后通知等待者。下面先只看读线程让出 CPU 邻近的分支。

~~~text
A 检查条件未满足 → 准备睡眠 → schedule
 → __schedule 取本 CPU 的 rq、锁住队列、更新时间
 → 检查切换方式、prev 状态及待处理信号
 → 需要睡眠则 deactivate_task
 → pick_next_task 决定 next → prev 和 next 不同时执行 context_switch
~~~

源码摘录 `kernel-6.1/kernel/sched/core.c:6449–6454`

~~~c

{
	struct task_struct *prev, *next;
	unsigned long *switch_count;
	unsigned long prev_state;
	struct rq_flags rf;
~~~

先看当前任务是否因睡眠离开运行队列，再看 pick_next_task 是否选中不同任务。

源码摘录 `kernel-6.1/kernel/sched/core.c:6531–6536`

~~~c

	next = pick_next_task(rq, prev, &rf);
	clear_tsk_need_resched(prev);
	clear_preempt_need_resched();
#ifdef CONFIG_SCHED_DEBUG
	rq->last_seen_need_resched_ns = 0;
~~~

源码把 prev_state 读到局部变量，再判断是否为抢占模式。普通阻塞场景中，如果当前等待状态可被待处理信号打断，就恢复 TASK_RUNNING；真正睡下时才带 DEQUEUE_SLEEP 从队列摘掉。普通抢占时 A 仍可运行，之后可以重新被挑中。按这个区别读自愿切换与非自愿切换计数，避免单凭计数给原因定性。pick_next_task 也可能选回 prev，此时已经进入调度器，但未发生任务间切换。

**用条件变量推一遍。** 若 A 在入睡前被信号唤醒，画出“进入 schedule，发现不能再睡”的分支。若 A 只是被普通抢占，写出为什么 B 退出后还能重新选到 A。最后解释这两种路径为什么不能合并成一句“进入 schedule 就摘掉当前任务”。

## 3.2.3 从唤醒事件到目标 CPU

~~~text
写者公布数据 → 等待队列回调 → try_to_wake_up
 → 检查任务等待状态与队列归属
 → 必要时将任务标为 TASK_WAKING，选择目标 CPU
~~~

在 try_to_wake_up 先看与传入等待状态掩码的匹配。若任务已经在队列上，核心会处理该情形，无需当作一个全新任务再入队。真正已睡下的任务走选择 CPU 和排队；SMP 中还需与旧 CPU 上的切换完成同步。检查 ttwu_queue 中的远端 wake list 快路径，并对照同一个函数在其他情况下如何直接加锁完成激活。目标 CPU 受亲和性、调度类和当前负载约束。目标核有新的候选任务后，check_preempt_curr 决定是否需要设置重新调度的请求。唤醒动作可以由写者或中断相关路径发起，真正选择 next 仍发生在目标 CPU。

**反例。** 两个写者都更新条件并试图唤醒 A。若唤醒只做无保护的“加到队列末尾”，就会把同一任务入队两次。回到源码找 p->pi_lock、状态检查与运行队列锁各自守住的条件。读者真正醒来后仍要检查条件，另一读者可能已经先消费数据。详见[等待条件与唤醒](deferred-work.md)。

## 3.2.4 CFS 怎样记账，怎样挑一个实体

本版普通路径先从 rq_clock_task 和 exec_start 算实际执行时间 delta_exec。update_curr 分别加到 sum_exec_runtime 和经过权重折算的 vruntime。用近似公式理解 calc_delta_fair。

~~~text
虚拟时间增量 ≈ 实际执行时间 × NICE_0_LOAD / 实体权重
~~~

同一版 fair.c 把两个时间分别更新。这里选出实际记账的几行。

源码摘录 `kernel-6.1/kernel/sched/fair.c:905–909`

~~~c
curr->sum_exec_runtime += delta_exec;
schedstat_add(cfs_rq->exec_clock, delta_exec);

curr->vruntime += calc_delta_fair(delta_exec, curr);
update_min_vruntime(cfs_rq);
~~~

更新运行时间后，选择路径还须根据队列中的候选决定下一位。

源码摘录 `kernel-6.1/kernel/sched/fair.c:694–699`

~~~c
static inline u64 calc_delta_fair(u64 delta, struct sched_entity *se)
{
	if (unlikely(se->load.weight != NICE_0_LOAD))
		delta = __calc_delta(delta, NICE_0_LOAD, &se->load);

	return delta;
~~~

设 A 权重为基准权重的两倍，B 恰好等于基准。两者实际各跑 4 ms，则 A 的虚拟时间增加约 2 ms，B 增加约 4 ms。在两个任务长期争同一 CPU、始终可运行、没有组或配额干预的条件下，虚拟时间推进相近时，A 通常获得约两倍的 CPU 时间。这是长期份额的推导，不能从它给某个任务承诺具体的唤醒延迟。nice 经权重表改变权重，nice 数值本身不直接代入上式。

读 pick_next_task_fair 时，先识别普通调度队列中的最左候选，再看当前实体和其他选择规则如何参与，最后看有组调度时怎样走下一层队列。队列的 min_vruntime 追踪推进基准，具体选择还包含唤醒抢占和调度粒度。高优先级实时任务可以先于普通类候选运行。对比 SCHED_FIFO 与 SCHED_RR 时，先在同一实时优先级下说明队列行为：FIFO 没有同优先级轮转时间片，RR 额外有时间片轮转；两者仍会受更高优先级任务和调度约束影响。

### 时间片检查与唤醒检查来自不同入口

在周期性 tick 到达时，scheduler_tick 找到本 CPU 的 curr，更新时间，再交给当前调度类的 task_tick 方法。

源码摘录 `kernel-6.1/kernel/sched/core.c:5524–5529`

~~~c

update_rq_clock(rq);
thermal_pressure = arch_scale_thermal_pressure(cpu_of(rq));
update_thermal_load_avg(rq_clock_thermal(rq), rq, thermal_pressure);
curr->sched_class->task_tick(rq, curr, 0);
if (sched_feat(LATENCY_WARN))
~~~

输入是当前运行任务与它所在的 rq。这个回调可以记账，并根据具体策略请求重新调度。另一条入口是新任务变为 runnable，此时检查新候选是否值得抢占当前任务。周期记账与新候选比较都可能留下重新调度标记。真正的 next 仍然在后续调度点决定。对一次长等待，分别查线程在等待设备、等待上 CPU，还是运行中又被切出，才能选择正确的观察区间。

## 3.2.6 用系统现象检验推理

先查看 WSL 中有哪些可调度线程，以及当前终端任务允许在哪些 CPU 运行。命令只读取当前状态。

~~~bash
ps -eLo pid,tid,psr,stat,cls,ni,comm | sed -n '1,12p'
rg '^(Tgid|Pid|Cpus_allowed_list|voluntary_ctxt_switches|nonvoluntary_ctxt_switches):' "/proc/$$/status"
~~~

PID/TID 用于区分线程组和任务。PSR 是最近执行所在的 CPU，不能用它替代 CPU 亲和性。切换累计值可用于前后差分，但不能给单次延迟配对。若已有 sched 事件，尝试以下练习，各时间戳假设在同一时钟域。

| 时间 | 事件 | 如何解释 |
| ---: | --- | --- |
| 10.000 ms | 设备报告完成 | 还需查驱动有没有发布完成队列 |
| 10.060 ms | sched_wakeup 的 pid 为 204 | 为目标线程记录唤醒时间 |
| 10.400 ms | sched_switch 的 next_pid 为 204 | 此次唤醒到切入约 340 µs |
| 10.470 ms | TID 204 打印 DQBUF 返回 | 切入到用户态记录约 70 µs，含此区间内的执行与可能等待 |

碰到丢事件、复用 TID、跨 CPU 时钟不一致，应先判定能否配对。若调度记录从中间开始，只见 switch 没有 wakeup，不能拿上一帧或另一个线程的事件补齐。若线程被抢占后保持 runnable，后来重新切入，也未必有一个新的 wakeup，要用上一条切出状态解释。以上是离线示例，板端案例的测量点见[帧等待时间线](process.md#wakeup)。

## 3.2.7 本节复盘

1. **线程为何被唤醒却没有立刻运行？** 先说明等待条件怎样变成满足，再说明任务进入目标 CPU 可运行集合，最后由调度点和调度类决定实际切入。补充两个可能限制，例如亲和性与更高优先级候选。最后指出需配对 wakeup 和 switch 才能量化。
2. **系统调用一定触发上下文切换吗？** 用同一线程的 EL0/EL1 变化与 prev/next 更替分别解释。无阻塞的简单调用通常一路用当前线程完成，阻塞读取才可能进入调度路径。
3. **为什么提高采集线程优先级仍可能卡？** 线程若等设备、空槽或锁，优先级本身不能让条件成立。若低优先级持锁者被中优先级任务抢占，则可能出现优先级反转。先查持锁路径、等待窗口以及锁是否提供优先级继承。
4. **怎么把这知识用在本板？** 对同一帧标出设备完成、VB2 发布、线程唤醒、线程切入、应用出队。若主要延迟位于唤醒之前，继续查设备完成与驱动等待。若唤醒到切入明显长于基线，再查竞争、迁移与亲和性。已有短采集帧间隔只能说明到达节奏，无法填满这一整条时间线。
