录像文件的两个名字都删掉以后，一个早先打开它的进程还能读吗？先实测名字和 fd，再沿 VFS 和 ext4 追踪资源的寿命。

## 打开、删除和继续读

在 WSL 仓库根目录运行。程序在当前挂载创建并清理自己的临时目录，要求文件系统支持硬链接。<a :href="exampleFile" download="unlink_lifetime.c">下载完整 C 实验</a>。

~~~bash
findmnt -no TARGET,SOURCE,FSTYPE -T .
mkdir -p output
cc -std=c11 -O2 -Wall -Wextra -Werror learning-site/examples/unlink_lifetime.c \
  -o output/unlink-lifetime
./output/unlink-lifetime
~~~

本轮实验在 WSL 的 ext4 上完成。设备号和 inode 号随环境和运行变化，同一次实验的 fstat 结果应保持身份不变。

| 操作完成后 | 按名字查找 | 用 fd 取得的链接数 |
| --- | --- | --- |
| 先 open，再加一个硬链接 | clip 和 second 指向同一个 dev + inode | 2 |
| 删除 clip | clip 返回 ENOENT，second 仍能定位同一文件 | 1 |
| 删除 second | second 返回 ENOENT | 0 |

最后对旧 fd 调用 pread，仍读到 frame。pread 显式指定偏移 0，因为先前 write 已推进普通文件偏移。这个对照验证名字和引用的寿命。5 字节样本、文件系统元数据和并发活动无法给出准确的空间回收量。

## 挂载、名字、文件和描述符各持有什么？

| 对象 | 持有什么 | 观察入口 |
| --- | --- | --- |
| 挂载命名空间与挂载实例 | 进程可见的挂载树。挂载实例连接一个根 dentry，也有挂载属性 | findmnt -T 目标路径，或进程的 /proc/PID/mountinfo |
| super_block | 文件系统实例的类型、操作与实例级属性 | 同一文件系统实例可经不同挂载到达 |
| dentry | 路径分量的名字与父项、关联 inode 的缓存状态 | 负 dentry 可记住暂时未找到的名字 |
| inode | 对象的权限、长度、链接数、数据映射和操作表 | 用 dev + inode 比较同一时刻的对象，nlink 表示目录硬链接数 |
| struct file | 一次打开的状态、路径引用、位置和操作表 | dup 或继承可共同持有一个 file，独立 open 通常各有游标 |
| fdtable | 整数槽位及其 file 引用 | /proc/PID/fd 或从进程内用 fstat 查询 |

~~~text
路径 → 按挂载树逐段查找 → 取得 dentry 和 inode → 创建 file → fd
                            ↑                               │
unlink 从父目录移除名字 ────┘                               │
pread 从已有 fd 查 file 和操作表 ←──────────────────────────┘
最后引用结束 → 文件系统按自己的事务与回收规则释放对象
~~~

## unlink 改的是谁？

内核检查删除权限、挂载点和安全钩子。从**父目录**的 inode 操作表分派，dentry 表示要移除的孩子。

`fs/namei.c:4322`

~~~c
error = dir->i_op->unlink(dir, dentry);
if (!error) {
	dont_mount(dentry);
	detach_mounts(dentry);
}
~~~

普通成功路径随后更新缓存状态并发出通知。已有 file 继续持有先前取得的对象引用，读取时经 file 分派。

源码摘录 `kernel-6.1/fs/namei.c:4299–4304`


ext4 的正常分支先在事务中移除目录项。删除目录记录成功后，还会更新目录元数据。


## 最后谁释放打开引用和数据块？

close 先摘掉整数槽位。dup、继承或文件映射都可能仍持有打开对象。到最终 fput 清理，VFS 才归还 file 的路径引用，处理可能随调用上下文延后。

`fs/file_table.c:328`

~~~c
dput(dentry);
if (unlikely(mode & FMODE_NEED_UNMOUNT))
	dissolve_on_fput(mnt);
mntput(mnt);
~~~

dput 与 mntput 归还 dentry 和挂载的引用。inode 的回收还要看其他持有关系和文件系统行为。ext4 驱逐无链接 inode 时，正常删除路径会先将长度置零，再按已分配块情况截断。

`fs/ext4/inode.c:285`

~~~c
if (inode->i_blocks) {
	err = ext4_truncate(inode);
	if (err) {
~~~

成功的清理路径还要处理 orphan 状态和磁盘 inode。事务或 I/O 失败会影响实际回收。实验只验证到关闭以前的最后一次读，未跟踪日志提交或分配位图。普通缓冲读取和写回使用 inode 的 address_space。两个独立 file 可以有各自的偏移，同时访问同一文件的数据缓存。

## 录像名字删了，空间为什么还有压力？

先对实际录像路径执行 findmnt -T。板端缺少 findmnt 时，可通过目标进程的 mountinfo 查看可见视图。根分区是 ext4 时，SD 卡及其他分区仍可能不同。

| 需确认的假设 | 证据 |
| --- | --- |
| 还有硬链接 | 读取剩余名字或打开 fd 的 nlink，在同一文件系统核对对象身份 |
| 进程拿着已删文件 | 在有权限的 /proc/PID/fd 查带 (deleted) 的路径提示，核对 dev、inode 与 nlink。另查进程仍持有的文件映射 |
| 逻辑大小与占块差异 | 对照 st_size 与 st_blocks，考虑空洞、预分配及待写回数据 |
| 持有者退出后仍有差异 | 对齐同一挂载的空间读数，并检查同期新录像、错误或事务活动 |

先保留原始返回码和活动引用。本轮验证了 WSL 临时文件和 ext4 场景，板端录像挂载及回收时机需要单独核实。
