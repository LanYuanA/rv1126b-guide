# Linux 内存管理实现

地址空间、页表、页分配器各自回答一个问题。虚拟地址是否合法，CPU 如何翻译，以及要新页时从哪里取得。可以先从[3.7 的逐页写实验](virtual-memory.md)开始，再在本页按函数查阅主线。

## 1. mmap 建立范围，CPU 访问建立翻译

进程的 mm_struct 管理用户地址空间。vm_area_struct 记录范围、权限、文件和映射偏移等信息。页表项则记录一页当前如何被翻译及保护。看 do_mmap 中长度、地址和标志检查，再跟到 mmap_region。合法 VMA 中可以暂时没有有效的末级页表项。CPU 的 TLB 未命中也可能通过已有页表解决。

<Sdk id="mm-mmap-range" />

mmap 建立可访问范围。真正访问后若翻译或权限触发异常，才来到架构缺页入口。

<Sdk id="arm64-page-fault" />

~~~text
写用户地址 → ARM64 同步异常 → 检查 VMA 和写权限
 → handle_mm_fault → __handle_mm_fault 构建或遍历页表层级
 → handle_pte_fault 根据当前映射状态分流
~~~

逐级找到末级位置后，按那里的页表项状态决定分支。

## 2. 四条需要区分的分支

| 页表和访问情况 | 源码分流 | 结果 |
| --- | --- | --- |
| 匿名地址的合法首写 | do_anonymous_page | 准备零初始化的页并安装可写映射 |
| 文件地址的首次访问 | do_fault 等文件映射路径 | 内容可能已在页缓存，也可能要等待 I/O |
| 私有可写区在 fork 后首次写受保护页 | do_wp_page，必要时 wp_page_copy | 写者取得自己的数据版本，独占时可能复用 |
| 地址无 VMA 或访问不被允许 | 架构入口检查后报告错误 | 用户访问可能收到 SIGSEGV；某些文件访问错误可能为 SIGBUS |

<Sdk id="vm" />

匿名访问可以准备匿名页。带 vm_ops 的文件映射另有缺页处理。

<Sdk id="mm-file-fault" />

首次文件缺页与已有页表项上的写保护异常，分别在不同条件进入。

<Sdk id="wp-fault" />

写保护分支可以判断是复用页还是需要复制。只有后者沿下面的路径准备新页。

<Sdk id="wp-copy" />

跟匿名写时，从申请页追到设置页表项。跟 COW 时标明修改的是写方的 PTE，即使父子看到相同的虚拟地址，其写入之后也可以对应不同物理页。页表变化涉及 TLB 的一致性维护，不能只改软件结构就假设 CPU 会忘掉旧翻译。

## 3. 谁提供页，谁提供对象

伙伴系统根据 zone、order 与迁移类型选择页块。分配压力下可能回收或迁移，取决于请求约束与 GFP 标志。SLUB 从页上切出可复用的小对象，释放对象与整个 slab 的页归还分别计时。CMA 解决特定区域的物理连续要求。vmalloc 拼出连续的内核虚拟区，底层页可离散。用 DMA API 获取设备能用的地址，这一层与进程缺页各有自己的映射和访问协议。见[伙伴系统](page-allocation.md)、[SLUB](slub.md)和[DMA 地址](dma-ownership.md)。

## 4. 本节复盘

- **mmap 一成功，RSS 就增加整个长度吗？** 地址范围与驻留页分别统计，需看预触页、映射文件、实际访问和大页策略。
- **minor fault 算不算故障？** 它可以是正常首触或 COW。先看访问是否最终成功，再解释是否需要 I/O。
- **还有可用内存，分配为什么会失败？** 用所需 order、zone、可等待性和地址约束逐级缩小范围。相机 REQBUFS 还要核对每个 plane 和实际 VB2 allocator。
