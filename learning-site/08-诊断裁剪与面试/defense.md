一句“做过 IMX415 适配”要经得起三个追问。哪段是你亲手完成的？能指出哪个资源或函数？什么观察会推翻你的解释？准备报告时给每条成果写上原始证据、操作条件和剩余问题。

## 一页报告怎样写

| 记录项 | 需要写下什么 |
| --- | --- |
| 背景与约束 | 板卡、sensor、内核提交、镜像、工作模式、测试场景、已有服务与权限 |
| 本人负责 | 实际读过、编过、改过、测过哪部分。标明共同参与者、原厂基线和个人改动 |
| 发现问题 | 首个出错位置、命令、错误日志及窗口 |
| 竞争假设 | 至少两个能解释症状的原因，以及分别会产生哪些证据 |
| 验证步骤 | 同输入基线、一个主要变量、恢复复测；失败也保存 |
| 结果与边界 | 报实际样本量、指标口径、源码位置和未覆盖条件 |

给证据打标签便于读者理解。**历史板端记录**说明当时原厂镜像的事实。**本地交叉编译**说明候选构建。**WSL 实跑**可以证明软件路径、工具输出和反例。**离线模型**用于验证计算、状态或假设。只有同一次实板运行的相关数据才能直接评价那次硬件状态。

## 案例一，能读到 ID 为何仍可能没有帧

**一分钟答法。** sensor 已经 ACK 且读回 0xe0，说明该次控制通道和 ID 校验成立。接下来查 mode/stream 是否执行、CSI/CIF 的 data lanes 与帧及错误、媒体 graph 的启用边、ISP 输出和 VB2 队列。I2C 负责控制与寄存器，真正的像素沿 CSI-2 进入接收器。两层应分别验证。

**代码追问。** DTS 首先由设备树描述节点，I2C 创建 client 后按匹配表交给 probe。probe 查电源、时钟、GPIO 和 ID，随后注册 subdev。应用从进程 fd 表经 VFS、字符设备和 V4L2 到 RKISP open，创建打开时的上下文；VIDEO STREAMON 才触发后续取帧。独立 open 可得两个 file，dup 共享原对象，两个 file 也可能竞争同一队列。 [4.12 I2C 入口](../04-设备模型与驱动子系统/i2c.md) · [5.10 RKISP 与视频节点](../05-相机驱动实践/rkisp-video-node.md)

**证据与反例。** 第一颗 IMX415 在 `3-001a` 报 ID 0xe0，原厂短流实际拿到有效数据。若只见 sysfs 设备名，没有 I2C ACK/ID，不能证明物理芯片正常。快速启动分支还可能使用已有状态或跳过某步，代码路径要和日志一起读。假如走完 STREAMON 之后 CIF 的包到达稳定而应用无 DQBUF，应把重点移到 downstream 格式、队列或调度。 [5.2 上电与读 ID](../05-相机驱动实践/first-power-id.md) · [5.11 VB2 完成](../05-相机驱动实践/vb2-queue.md)

## 案例二，vblank 859 µs 与短时 30 fps 如何同时成立

**一分钟答法。** CIF 报告的 online 阈值是 1000 µs；859 µs 是根据行时间和当前消隐行数算出的诊断量。原厂同一采集窗口仍有 31 次出队、0 序号缺口与一帧 12,441,600 字节 NV12。阈值触发与该轮短窗口成功可以同时成立。根因还需采集实际 mode、消隐、错误计数和负载变化。

**可以推翻什么。** 若在相同负载、多次重复中，消隐低于阈值时 upstream EOF 和错误计数均稳定，长间隔始终发生在 DQBUF 后的写盘端，则这批卡顿假设不应归给 CIF。若只有更改打印开关后日志消失，图像链指标仍可能完全相同。做单变量调整时还要监控 VTS 导致的帧周期和 3A 变化。 [8.2 告警与符号](./kernel-debug-log.md) · [8.1 采样口径](./performance-baseline.md)

**追到内核。** GIC 分派到驱动之后，从 IRQ action、VB2 完成、wakeup、sched_switch 到用户 DQBUF 时间分别取证。thread runnable 的等待只在唤醒和切入之间。若实际少了一条 trace 记录，报告不要给完整分段值。 [3.3 ARM64 中断](../03-Linux内核/irq.md) · [8.4 跨层时间线](./trace-timeline.md)

## 案例三，备录慢时怎样查反压和内存

**一分钟答法。** 同一个槽位从 DQBUF 交付给预览、主录、备录，分支拿引用又各自归还。先标明是同码流副本还是独立编码。记录 queue 水位、源 sequence、每支持有、编码完成和实际写盘。把备支接空 sink 或引入受控慢消费者，观测预览尾部与槽位空闲是否随单变量改变，再恢复原配置复测。

**追问缓冲。** 三块紧排 4K NV12 的有效容量约 35.6 MiB。mmap 建立用户地址映射，设备访问依赖 DMA 映射、分配器或 IOMMU。多个进程共享一块 DMA-BUF 时还有不同引用，RSS 简单求和不能代表物理占用。alloc/free 事件可检查一类对象，页、CMA 和 DMA-BUF 引用各有路径。监控结合多轮完全停流后的趋势，当数据中有观测缺口时降级。 [3.13 DMA 所有权](../03-Linux内核/dma-ownership.md) · [3.15 DMA-BUF 生命周期](../03-Linux内核/dmabuf.md)

**现有可复核结果。** WSL 的 FrameScope 合成例里，备录持有一帧 89 ms，槽位总持有 92 ms。另一份软件流水线在阻塞时预览最后一帧明显变迟，改丢帧策略时间提前但慢支少了帧。启停后的 4096 B 是离线夹具里故意留下的常驻池，工具没有把它判为泄漏。板端还需要接收这些实时事件。 [6.4 队列和反压](../06-相机应用与分流/gst-queues.md) · [8.8 FrameScope 原型](./framescope.md)

## 简历只写自己能当场复现的事实

可以按“职责 → 实际做法 → 实际结果 → 使用条件”写。以下作为模板，请用自己已经独立完成的工作替换职责和数据。

- 相机基础　“在 RV1126B 原厂 Linux 6.1.141 固件上复核 IMX415 控制与图像链路，使用媒体拓扑和 V4L2 出队日志验证 3840×2160 NV12；在约 1 秒窗口复算 31 帧、观测速率 30.000 fps，并定位 CIF 的消隐告警表达式。”
- WSL 原型　“用单合成源验证预览、主备录像与 JPEG 并发，编写离线帧和资源关联原型，可报告持槽、序号缺口、活跃分配及不完整证据。”
- 内核调试　“交叉编译候选 ARM64 内核产物，验证 Kconfig 依赖求解与同构建 DWARF 符号化；拆分 BPF 可用性、追踪时间线和 CPU 热点观测。”

候选内核运行、新板自主适配、板上四路硬编、HDR、AI ISP、量产启动优化和实机 BPF，分别在有对应结果之后才写作实现。独立复现后，记录本人命令、回滚办法和一次失败，容易回应简历延伸问题。
